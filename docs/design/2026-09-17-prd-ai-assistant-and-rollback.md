## 1. 产品目标

在不动摇「判定引擎（`JudgeEngine`）是唯一判定权威」与「审计流水不可篡改」两条底线的条件下，为一线人员加装两个「省时 + 纠错」的增强能力：一个只谈检验业务、能联动本地 GB 标准库做秒级检索与**建议性引用**的悬浮 AI 助手；一套覆盖七阶段状态机、**分级授权、逐级可追溯**的流程回溯机制。

**可衡量目标**

- **G1 秒级检索**：对 ≥1GB 的 GB 标准库，单次检索 P95 ≤ 2s 返回 top-N 命中，且检索期进程内存不随库体积线性增长（举证：检索耗时埋点 + 内存采样）。
- **G2 助手聚焦**：抽样 100 条提问（含 30 条越界），越界请求 **100% 被拒答**，且拒答话术经评审为「同事口吻」而非系统报错（举证：拒答语料评审 + 询问日志）。
- **G3 建议可溯源**：AI 涉及标准/判定的一切输出 **100% 带标准号 + 条款出处**；AI 写入任何业务结论字段的次数 = **0**（举证：字段写入审计 + 抽查）。
- **G4 回退安全**：所有回退走**显式逆向白名单**，非法回退 100% 被拒并留痕；每次回退都能回答「谁 / 何时 / 从哪到哪 / 原因 / 是否可再撤销」（举证：流程回溯面板 + 流水查询）。
- **G5 历史不消失**：回退后历史数据 **100% 可追溯**（软删 / 留档，不物理删除），审计流水只增不改（举证：回退后原数据可查 + 无物理删除路径）。

## 2. 关键设计取向（设计张力裁决）★ 本次 PRD 核心

> 本节回答需求中的六处张力，给出**产品层取向**（不含技术实现）。

### T1 「绝不闲聊」与「有用」的边界

- **相关的定义**：命中以下任一即为相关 —— ① 本项目业务域（样品/七阶段状态机/角色权限/报告/判定规则/操作指引）；② 检验检测领域知识（标准条文、限量值、检测方法）。判定顺序：先过**领域护栏**（本地规则/分类）→ 命中即答；疑似检验问题 → 触发 **GB 检索**；仍不相关 → 拒答。
- **「水产品铅限值是多少」= 相关**：它属于 GB 2762 铅限量 + 水产品类别的领域问题，助手应检索标准库并**带标准号与条款出处**回答，但**只引用标准条文，绝不给出「合格/不合格」结论**。
- **拒答措辞（不作报错）**：像同事口吻，例如「这个问题超出本系统的业务范围，我主要负责检验业务、样品流程和标准查询——要不要我帮你查一下 XX 相关标准？」，并附 2–3 个可点击的替代建议。

### T2 GB 级标准库从哪来

- **交付的是「导入通道」，不是假设文件已存在**：首批由用户把 GB 标准文件（PDF / TXT / HTML）投放进**仓库内指定标准目录**，系统负责「解析 → 切块 → 建索引」；上传与建索引异步进行、可查看进度、可失败重试。
- **「GB 级」对交互的要求**：必须**预建索引**（MySQL `ngram` 全文索引可零依赖实现），检索**只查索引、绝不全量读文件**，保证秒级返回。
- **不承诺内置标准正文**（版权 + 体积），只承诺通道 + 检索能力 + 引用出处。

### T3 「辅助判断」的合规红线

- AI 的定位是**建议性引用**：找标准 / 解释条文 / 定位到具体条目 / 给操作指引，**必须带标准号与出处**。
- AI **不得写入任何业务结论字段**（判定值、单项结论、报告结论等），**不得静默判合格**。最终判定 **100% 仍由 `JudgeEngine` 闭集白名单矩阵产出并可审计**。
- **UI 上必须显式区分**：AI 输出统一标注「**AI 建议，仅供参考；判定以系统规则为准**」，与系统判定结论在视觉与文案上不可混淆。

### T4 「任意历史节点」回退的边界

- **回退只能逐级（每次退一步）**；「任意历史节点」在**查看层成立**（可回溯查看任意历史事件），在**回退层不成立**（禁止 S90 一路退回 S10）。
- **分级护栏**：
  | 分组 | 涉及 | 权限与要求 |
  |---|---|---|
  | 常规回退（未签发） | S20→S10、S30→S20、S40→S30、S50→S40、S60→S50 | 相应业务角色可退，**原因必填** |
  | 敏感回退（已审核） | S70→S60 | 需更高权限（R100 / R2）+ 强理由 + 二次确认 |
  | 已签发 | S80→S70 | 原则上**拒绝普通回退**；报告已对外生效，须走**作废 / 召回专门动作**并保留原签发记录 |
  | 已出报告 | S90→S80 | **拒绝回退**；数据已上报省平台，只能新增**更正 / 作废**记录 |
- **回退后原数据保留**：以软删 / 留档 / 新增版本方式处置，**绝不物理删除** —— 检验机构审计系统，历史不能凭空消失。

### T5 回退与「审核退回」的关系

- **统一为一套「流程回溯」机制**：既有的「审核退回 S60→S50」是其中一个**具名快捷动作**，底层与新增回退边**同一套逆向白名单、同一套留痕**。
- 遵守既有设计原则「正向与逆向不得合并」：新增回退边进入**独立逆向白名单**，不与正向 `VALID` 合并断言。
- **防混淆**：审核页保留「审核退回」快捷入口；列表行 / 详情页提供「回退」入口；独立「流程回溯」面板展示完整链路。三者行为与留痕一致，文案区分「退回 / 回退 / 作废」。

### T6 一致性：下游数据怎么办

- 回退**不静默删除下游数据**：分解明细 / 检验结果 / 审核流水等以「**失效 + 留档**」方式处置并可恢复；`sample_audit_log`、`sys_operation_log` **只追加不删**（回退本身也进流水）。
- **报告无独立数据表**：S90 回退不存在「删报告」，只更新 `sample_info` 状态；已生成 / 已上报的改为**作废 / 更正标注**。
- 一次回退只影响「被回退步骤及其下游」，执行前**弹窗列出将被置为失效的下游数据**（计数 + 清单）供用户确认。

## 3. 用户角色与场景

**6 类账号**：R100 管理员｜R2 业务管理员｜nj002 样品登记员｜nj003 任务管理员｜njsa000 / njna000 / njxa000 检验员｜nj001 审核签发人。

### 特性 A（AI 助手）

- 作为**检验员（njsa000）**，我希望录入结果时悬浮窗能直接查「GB ×××× 的方法要求」，以便不必离开页面翻 PDF 就能核对。
- 作为**样品登记员（nj002）**，我希望助手只回答检验业务问题、拒绝无关闲聊，以便工作不被打扰、不会得到不可信答案。
- 作为**审核签发人（nj001）**，我希望助手能解释某标准的判定条文并给出处，以便我理解依据，但**不替我做判定**。
- 作为**任务管理员（nj003）**，我希望助手能告诉我「某样品当前处于哪个状态、下一步该做什么」，以便少问同事。

### 特性 B（回退）

- 作为**检验员（njsa000）**，我希望发现结果录错时能回退到上一步并修改，以便不必整条重做。
- 作为**审核签发人（nj001）**，我希望回退已审核 / 已签发数据时系统强制更严格流程，以便对外报告不被随意改动。
- 作为**业务管理员（R2）**，我希望为敏感回退设置权限与必填理由，以便出错时可控、可追溯。
- 作为**检验员（njna000）**，我希望回退前看到会失效的下游数据清单，以便确认不会误伤已录入成果。

## 5. 交互设计说明（文字）

**AI 悬浮窗（特性 A）**

- **收起态**：右下角常驻小图标 / 气泡，不遮挡业务操作区，可一键隐藏。
- **展开态**：面板头部（标题 + 收起 + 关闭）+ 输入框 + 结果区；默认从右侧滑出。
- **会话态**：多轮对话列表；涉及标准时以**引用卡片**呈现（标准号、条款、出处链接），卡片明确标注「仅供参考」。
- **拖拽与位置记忆**：按住头部拖动到界面任意位置，边界内吸附；位置存本地，刷新 / 重登后恢复。
- **与页面业务检索联动**：页面上的搜索 / 标准引用入口可将**当前上下文**（样品 / 标准号 / 当前状态）带入悬浮窗，用户无需重复描述。
- **风格一致**：沿用 `Aurora Glass` 主题与 `--lims-*` 令牌；数据密集区遵循既有红线（不叠折射玻璃、强调色只做光晕 / 描边、动效 ≤ 0.45s）。

**回退（特性 B）**

- **入口**：① 列表行操作「回退」；② 详情页「流程回溯」按钮；③ 独立「**流程回溯**」面板（时间线）。
- **确认对话框必须展示**：从**当前状态 → 目标状态**｜将被失效的**下游数据（计数 + 清单）**｜**回退原因（必填）**｜是否需要**更高权限 / 二次确认**｜**不可逆提示**（涉及 S80 / S90 时重点提示）。
- 回退成功后，界面立即刷新该样品状态与可操作按钮，并在流程回溯面板追加一条事件。

## 6. 状态与记录设计（产品口径）

- 用户在界面应能看到一条完整回退记录：**操作人 + 时间 + 源状态 → 目标状态 + 原因 + 下游数据处置（失效 / 留档）+ 是否可再撤销**。
- **流程回溯面板**以时间线呈现该样品的**全部正向与逆向事件**，语义与追加型审计日志一致（既有的 `sample_audit_log` / `sys_operation_log` 口径）。
- **只增不改**：回退事件写入后不可编辑、不可删除；回退动作本身也必须被记录。
- 「可再撤销」状态需**显式呈现**给用户（可恢复 / 不可恢复），避免用户误以为随时能反悔。

## 7. 范围（In Scope / Out of Scope）

### In Scope

- 项目内 qwen3-4b 运行时与本地接入（零外发）。
- 领域护栏（只谈本项目）+ GB 标准库导入通道 + 秒级检索。
- 悬浮窗 UI（三态 / 拖拽 / 位置记忆 / `--lims-*` 一致 / 业务检索联动）。
- 统一流程回溯机制（逐级回退、分级授权、原因留痕、下游影响预览、软删留档）。
- 助手会话与回退事件的审计留痕。

### Out of Scope（逐条给理由）

| 不做 | 理由 |
|---|---|
| 调用云端大模型 | 用户要求**本地部署**；检验数据不出内网、合规要求 |
| AI 自动判定 / 写入结论 | 违反 `JudgeEngine` 唯一权威与「禁止静默判合格」，**红线** |
| 内置 / 预置 GB 标准正文 | 版权与体积问题；本次只交付**导入通道** |
| 物理删除历史数据 | 检验机构审计要求历史不可消失，只能用软删 / 留档 |
| S90 回退 / 跨级回退 | 已上报省平台数据只能**更正 / 作废**；回退只允许逐级 |
| 为助手引入 Markdown 重渲染依赖 | 条件性排除：优先用「结构化文本 + 引用卡片」呈现；确有必要再论证装包 |
