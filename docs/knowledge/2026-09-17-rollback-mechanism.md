# 全流程逐步回退（撤销/回滚）机制 —— 设计定稿与踩坑

> 日期：2026-09-17　实施：GLM
> 需求来源：**用户新增需求**（非业务说明书要求）——「为项目当前整套业务功能流程中的每一步操作实现回退机制」。
> 相关：`docs/design/2026-09-17-arch-ai-assistant-and-rollback.md`、`DECISIONS.md` 2026-09-17、`db/init/10_rollback_tables.sql`、`db/migrations/V8__rollback_and_ai.sql`

---

## 1. 一句话

在既有「正向 `VALID` + 退回 `RETURN`」两张白名单之外，**新增第三条独立白名单 `ROLLBACK`**，配合
「统一状态流水 + 回退记录 + 失效留档」三张表，把七阶段每一步做成**可逐级回退、可取证、可（有条件）再撤销**的动作。

---

## 2. 为什么必须是「第三条白名单」，而不是复用 `RETURN`

`SampleStatusTransition` 的既有设计原则是「**正向与逆向不得互相调用、不得合并**」（T-701 定稿）。
本次新增回退边时，很容易想到「把 S20→S10、S30→S20 等边也塞进 `RETURN`」——**这是错的**，两者语义不同：

| 维度 | `RETURN`（退回） | `ROLLBACK`（回退） |
|---|---|---|
| 语义 | **业务否定**：上一环节认为下游不合格，打回重做 | **纠错回滚**：操作者认为自己刚做的事做错了，撤回 |
| 触发者 | 审核人（下游角色的判断） | 操作者本人 / 有权管理者（自省式的撤回） |
| 数据处置 | **不动**下游数据（检验员自己重做） | **必须处置**下游数据（失效 + 留档） |
| 是否可再撤销 | 否（只能重新提交） | **是**（未产生新下游数据时可原路恢复） |
| 审计语义 | 一次质量判定事件 | 一次数据订正事件 |

**若合并**：`assertTransition` / `assertReturn` 的调用方将无法区分意图，单测也无法表达不变式，
未来任何新 Service 都可能把「退回」误当「回退」用（前者不该动数据、后者必须动数据）。

**结论**：三条独立 EnumMap、三个独立断言方法，互不调用。
`ROLLBACK` 当前**只有 6 条边**：`S20→S10`、`S30→S20`、`S40→S30`、`S50→S40`、`S60→S50`、`S70→S60`。

### 2.1 为什么 S80 / S90 没有回退边（红线）

- **S80 已签发**：报告已对外生效。撤销签发 = 撤回一份已发出的带 CMA/CATL 标识的报告，
  属于**资质行为**，不是「改个状态」。用 `report_void`(作废/召回) 动作**只写标记、不改 `status`**，
  保留原签发记录，由业务另行处理。
- **S90 已出报告**：数据已上报省平台。回退等于让已上报数据与系统状态不一致 → **拒绝**，只能新增更正/作废记录。

这条红线不是「界面把按钮藏起来」，而是**白名单里根本不存在这条边** —— 藏在 UI 层的约束一定会被绕过。

## 3. 数据层方案：为什么是「版本化留档」而不是「快照还原 / 反向补偿」

三种候选：

| 方案 | 做法 | 裁决 |
|---|---|---|
| **快照还原** | 每步把该样品相关表的所有行序列化存下来，回退时整表覆盖回去 | ❌ 排除 |
| **反向补偿** | 为每个操作写一个「逆操作」，回退时执行逆操作 | ❌ 排除 |
| **版本化留档**（采纳） | 失效前整行 pre-image 存 `sample_data_archive`，主表**置失效**（不物理删）；回退只做「状态逆流 + 失效下游 + 留档」 | ✅ 采纳 |

**排除快照还原的理由**：本项目是**检验机构审计系统（ALCOA+）**。快照覆盖回主表会让
「这一行的这段历史从未存在过」成为事实——事后无法回答「当时是谁录了什么」。
而且快照是「某个时刻的整体像」，与既有「覆盖式 upsert + 审计四字段」的增量留痕机制**两套真相并存**。

**排除反向补偿的理由**：逆操作要逐个操作手写（`ItemServiceImpl.saveDecompose` 的逆操作 ≠
`ResultServiceImpl.save` 的逆操作），漏一个就是静默的数据损坏；且逆操作本身是**代码**，
升级后语义会漂移，历史回退行为不可复现。

**留档方案的关键性质**：
- 回退**只改状态 + 置失效 + 留档**，绝不物理删除 → 满足用户要求的「历史不消失」与审计要求。
- `sample_data_archive.snapshot_json` 保留**失效前的整行**（含 `deleted` 原值），取证时可完整还原「当时那一行长什么样」。

## 4. ⚠️ 最高风险改动：`deleted` 语义从「0/1」升级为「0 / 行自身 id」

### 问题

`sample_item` 的唯一键是 `uk_sample_item_order(sample_id, item_order, deleted)`。
`ItemServiceImpl.saveDecompose` 是**覆盖式重建**：先 `deleted=1` 删除全部旧明细，再全量 INSERT。

于是——**同一行被逻辑删除两次必然撞唯一键**。而回退机制恰恰会产生「反复失效/恢复」，
第一次回退把新行置失效（`deleted=1`），第二次回退时旧行已经是 `deleted=1` → **撞键，回退失败**。

### 实测结论（重要）

MyBatis-Plus 的 `@TableLogic`（以及 `logic-delete-value` 配置）**只支持固定字面量**，
**不支持表达式**（无法表达「置为行自身 id」）。

### 处置

- 保留 `logic-delete-value: 1` —— 它只作用于**读写过滤**（`WHERE deleted = 0`），这部分语义不变。
- 业务侧的「失效」写入**不再走 `removeById` / 实体 `update`**，改为**原生 `@Update` SQL**：
  把 `deleted` 置为该行自身 `id`，配合 `deleted <> 0` 作为失效判据。
- **必须全仓清理硬编码 `deleted = 1` 判定**。任何 `eq("deleted", 1)` / `if (deleted == 1)` 都是 bug
  （它会把「已失效」错判为无效条件，因为新语义下失效值 ≠ 1）。

### 为什么值得冒这个风险

替代方案是「唯一键去掉 `deleted` 列 + 新增 `void_ver` 版本列」，但那要动**既有唯一键**（影响 T-401 以来所有写入路径），
改动面更大。`deleted` 语义升级把影响面收敛在「失效写入」这一个动作上，且 `deleted<>0` 与 `deleted=0`
的二分语义在所有既有查询里仍然成立。**但这是本项目最需要回归验证的一处改动**。

## 5. 回退执行的四条硬性不变式（已用单测固化）

1. **状态变更走乐观条件 UPDATE**：`WHERE id=? AND status=旧值`，`updated==0` → 业务码 **4108**
   （「样品状态已变更，请刷新」）。与既有 9 处流转完全同构——回退也是并发敏感动作。
2. **失效处置必须在状态 UPDATE 之后、同一事务内**。顺序反了会出现「数据已失效但状态没退」的中间态，
   而这个中间态**看起来是正常的**（状态没变、数据没了），排查成本极高。
3. **一次回退在 `sample_status_log` 新增且仅新增 1 条 `event_type=4` 记录**，
   其 `(from_status, to_status, rollback_id)` 必须与 `sample_rollback` 行一致。
   —— 用 `InOrder` + `verify(..., times(1))` 固化，而不是靠注释声明。
4. **绝不物理删除**：`sample_audit_log` / `sample_status_log` / `sys_operation_log` 只增不改；
   `sample_item` / `sample_result` 只置失效。

## 6. 三处「破坏性写」是怎么被覆盖的

回退机制的价值取决于它是否覆盖了**真正会丢数据的操作**。设计前侦察出的三处：

| # | 破坏性写 | 风险 | 回退处置 |
|---|---|---|---|
| 1 | `ItemServiceImpl.saveDecompose` 覆盖式重建 `sample_item` | 旧分解明细变 `deleted=1`，且新行替换了 `item_order` | 失效前留档；唯一键问题见第 4 节 |
| 2 | `ResultServiceImpl.upsertResult` 覆盖式 upsert，**旧 `test_value` 原始值被直接覆盖** | ALCOA+ 要求原始值可追溯 | 保存前**修订留档**（`archive_reason=2`）——注意这条**不只是回退时才触发**，正常重复保存也会留档 |
| 3 | `sample_item` 覆盖式重建后，`sample_result.sample_item_id` 指向已失效的 item | **孤儿引用**：结果行还在，但它的 item 已失效 | 回退时一并失效 + 留档；`V8` 迁移内置校验 SQL 断言无孤儿 |

第 2 条是本轮的一个**额外收获**：为了让「回退到重新录入」时能回答「用户看到的是哪个值、旧值还能不能取证」，
不得不给正常的覆盖式保存也加留档 —— 顺带补上了一个既有的 ALCOA+ 缺口。

## 7. 「任意历史节点」的落法：可跨级看，不可跨级退

需求原文是「回退到上一状态**或任意历史节点**」。落地取舍：

- **查看层**：`sample_status_log` 让「任意历史节点」成立 —— 时间线可回溯该样品**全部**正向与逆向事件。
- **回退层**：**只允许逐级退**（每次退一步）。

**理由**：跨级回退（如 S70 一步退到 S40）意味着同时撤销 3 个环节的产出，而每个环节的失效/恢复语义不同
（S60→S50 要动结果、S50→S40 要动分配、S40→S30 要动分解）。一次调用里串起 3 套处置逻辑，
失败时**没有原子回滚的落点**（数据层已经动了）。逐级退让每一步都可验证、每步都留一条流水，
出错时能精确定位是哪一步的问题。用户要的是「有更改余地」，逐级退完全满足，而跨级退带来的是不可控。

## 8. 与既有「审核退回」的关系（防混淆）

- 统一为一套「流程回溯」：`sample_status_log` 同时承载 `event_type=1`（正向）`2`（审核退回）
  `3`（签发）`4`（回退）`5`（恢复）`6`（作废/召回）`7`（报告生成）。
- **行为与留痕一致**，但 UI 上三者文案必须区分：**退回**（质量判定）/ **回退**（数据订正）/ **作废**（报告治理）。
- 既有 `sample_audit_log` **保留不动**（它是审核域的原始凭据）；`sample_status_log` 是更高层的统一时间线。
  两者是「域内凭据」与「跨域时间线」的关系，不是重复。

## 9. 可复用结论（给同类项目）

1. **逆向动作要按「语义」分类，不要按「方向」分类**。同样是「往回走」，业务否定与纠错回滚的
   数据处置要求完全不同；合并成一张表迟早出事。
2. **审计系统里，回退 ≠ 删除**。回退是「新增一条反向事件 + 置失效 + 留档」，主表永远只增不改。
3. **唯一键含 `deleted` 是陷阱**。只要该键需要「同一行多次失效」，`TINYINT 0/1` 就不够用，
   必须上「行自身 id」或独立版本列。设计阶段就要问「这张表会不会被反复失效」。
4. **给覆盖式写入加「保存前留档」是低成本高回报**。它把「覆盖式 upsert」从「丢历史」变成「可取证」，
   而且实现的是一段通用逻辑（留档 + 覆盖），不是每个业务写的逆操作。
5. **红线要落在白名单里，不要落在 UI 里**。`S80/S90 不可退` 如果不是「表里没有这条边」，
   迟早会被新代码绕过。
