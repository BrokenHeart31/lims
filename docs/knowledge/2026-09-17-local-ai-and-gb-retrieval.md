# 项目内本地大模型（qwen3-4b）+ GB 标准库检索 —— 选型、踩坑与复现

> 日期：2026-09-17　实施：GLM
> 需求来源：**用户新增需求**——本地模型 AI 助手，需部署进项目目录、严格限定只答本项目问题、
> 能检索 GB 级本地标准库、辅助判断、可拖拽悬浮窗、UI 与项目一致。
> 相关：`docs/design/2026-09-17-arch-ai-assistant-and-rollback.md`、`db/init/11_ai_tables.sql`、`ai/`

---

## 1. 三条决定整个方案的技术事实（先验证，再设计）

本项目 Maven 是**离线本地仓**，这一条约束几乎决定了所有选型。设计前实测得到：

| # | 事实 | 对方案的影响 |
|---|---|---|
| 1 | 离线仓**没有** `spring-boot-starter-aop` / **Lucene** / **PDFBox** / **Tika** / langchain4j；**有** `spring-ai 1.0.0-M6`（M 里程碑，兼容性未验证）、POI 4.1.2、**jsoup 1.18.3**、jtokkit | 不能引 AI 框架、不能引搜索库、不能引 PDF 解析库 |
| 2 | JDK 17 自带 `java.net.http.HttpClient`；Spring MVC 自带 `SseEmitter` | **零新依赖**调 Ollama + 流式输出（不需要 WebFlux） |
| 3 | MySQL 8.0.45 `ngram` 解析器 **ACTIVE**，`ngram_token_size=2` | **零新依赖**实现中文全文检索 |

> **决策口径**：能零依赖做的一律零依赖。唯一新增的 Maven 依赖是 `jsoup`（HTML 解析），
> 因为「从标准库 HTML 里抠正文」没有 JDK 内置替代。

**spring-ai 0.0.1-M6 为什么不用**：M 里程碑版本 + 离线仓传递依赖完整性未验证 +
本项目只需要「一次 HTTP POST + 读 NDJSON 流」这一步，用 200 行 `HttpClient` 封装可控性更高
（超时/拒绝/非200/流中断要分类处理，框架反而挡住这些细节）。

## 2. 模型落地：为什么是「Ollama 便携版 + 项目内目录」

用户要求「部署到 lims 这个项目文件夹中」（可随项目整体搬走，不散落用户主目录）。落地方式：

| 项 | 值 |
|---|---|
| 运行时 | `ollama-windows-amd64.zip`（**便携版，非安装包**）解压到 `ai/runtime/` |
| 模型目录 | 环境变量 `OLLAMA_MODELS` 指向 `ai/models/`（**必须在启动前设置**，否则模型默认落到 `C:\Users\<用户>\.ollama`） |
| 模型 | `qwen3:4b` —— 4.02B Dense / Q4_K_M / **2.5GB** / Apache-2.0 |
| API | `http://127.0.0.1:11434`，`/api/chat`（`stream:true` 返回 NDJSON）、`/api/tags`（健康检查） |

**为什么不用 OllamaSetup.exe**：安装包强制写入系统盘且注册为 Windows 服务，与「随项目搬走」的目标冲突。
便携版解压即用 + 环境变量定向，整个 `ai/` 目录可整体拷贝到另一台机器。

**qwen3 的思考模式必须显式关闭**：qwen3 系列默认开 thinking，会在正文前吐出大段推理内容。
对交互式助手这会**同时**造成两个问题：延迟显著拉高 + 用户看到思考过程的噪音。
Ollama API 传参数关闭。

**注意 `qwen3:4b` 与 `qwen3:4b-instruct` 是两个 tag**：后者是非思考模式变体，同为 2.5GB，
对「短问答型助手」更贴合。本项目用的 `qwen3:4b` + 显式关思考，等价效果且保留可切回的余地。

**硬件门槛**：Q4_K_M 约 2.6GB 权重 + 约 1.5GB 运行时开销 ≈ **4.1GB 显存**；纯 CPU 可跑但约 1~5 tok/s。
把这条写进交付说明——否则用户会在没有独显的机器上认为「AI 坏了」。

### ⚠️ 沙箱/CI 环境无法下载大文件

本次实施环境（沙箱代理）对 GitHub Release 大文件返回 **502**，实测 **7 条路径全部失败**：
GitHub 直连、`ghfast.top`、`gh-proxy.com`、`ghproxy.net`、`gh.llkk.cc`、`hf-mirror.com`、`modelscope`。

**因此交付形态是「一键部署脚本 + 手动兜底说明」，而不是「已部署好的模型」**：
- `ai/scripts/deploy-ollama.ps1` —— 内置多镜像候选 + 失败自动换源 + 手动下载兜底提示
- `ai/scripts/start-ollama.ps1` / `stop-ollama.ps1` / `status-ollama.ps1`
- `ai/scripts/prepare-standards.py` —— GB 文件预处理（PDF→TXT，见第 4 节）

**给同类项目的教训**：涉及大文件下载的部署步骤，**必须假设目标环境可能下载失败**，
把「多镜像 + 手动兜底 + 状态自检」做进脚本，而不是写一句 `curl` 了事。

## 3. ★ MySQL ngram 中文全文检索：三个实测踩到的坑

`ngram` 解析器让 MySQL 零依赖支持中文全文检索，但**行为与英文全文检索差异很大**，以下是实测撞出来的：

### 坑 1：单字检索词被直接丢弃

`ngram_token_size=2` 意味着索引里只有 2-gram。**检索词长度 < 2 时匹配不到任何东西**
（不是「匹配少」，是「恒为空」）。用户输入「铅」这种单字项目名是**很常见**的（重金属项目名多为单字）。
→ 处置：检索前做**最小长度校验/词扩展**，并对单字给出明确提示而不是返回空结果假装没找到。

### 坑 2：`innodb_ft_min_token_size` 对 ngram 不生效

英文全文检索里控制最小词长的是 `innodb_ft_min_token_size`，于是很容易去调它。
**但用 `WITH PARSER ngram` 的索引，其行为由 `ngram_token_size` 决定**，改前者无效。
调错参数会让人得出「配置改了但没生效」的错误结论。

### 坑 3：`MATCH(...)` 的列清单必须与 `FULLTEXT` 索引列**完全一致**

否则 MySQL 直接报 **1191**（`Can't find FULLTEXT index matching the column list`）。
`gb_clause` 只对 `content` 建了 `ft_gbc_content`，因此**任何** `MATCH` 都只能写 `MATCH(content)`。
如果想要「标准号 + 正文」联合检索，必须另建一个覆盖两列的 FULLTEXT 索引，不能临时拼列。

### 其余注意点

- **句法**：布尔模式（`IN BOOLEAN MODE`）里 `+词` = 必须含、`"短语"` = 精确短语、`-词` = 排除。
  回退策略（`+A +B` 无命中时降级为 `A B`）是实用技巧，但要保证**降级后的结果仍标注为降级**
  （否则用户以为「这些是精确命中」）。
- **排序**：用 `MATCH(...) AGAINST(...) AS score` 的得分排序，不要用 `LIKE` 兜底排序
  （`LIKE '%x%'` 会退化成全表扫描，GB 级数据下秒级目标立刻失守）。
- **只查索引、绝不读文件**：这条是「秒级」能否成立的前提。检索路径里**不允许出现任何文件 IO**。
- **索引表允许物理重建**：`gb_clause` 是**可由原始文件随时重建的派生数据**，不是业务留档。
  换版标准时物理 `DELETE` 旧 clause 再重建是正确做法 —— 「历史不消失」约束**不适用**于检索索引。
  这点必须在设计文档里写明，否则后人在「审计系统禁止删数据」的原则下会不敢重建索引。

## 4. GB 标准文件的导入通道（PDF 的坑）

**没有 PDF 解析库可用**（离线仓无 PDFBox/Tika）。三种候选：

| 方案 | 裁决 |
|---|---|
| 引入 PDFBox | ❌ 离线仓拿不到；且会为一个**静态批处理**需求给运行时加依赖 |
| 后端只收 TXT/HTML/MD/CSV，PDF 直接拒收并给指引 | ✅ 采纳（配合下面的预处理） |
| 离线预处理脚本把 PDF 转文本 | ✅ 采纳 |

**最终形态**：`prepare-standards.py`（pypdf，纯离线批处理）先转文本 → `import-standards.ps1` 串成一条命令 →
后端只处理已转好的文本/HTML。后端对 `.pdf` **fail-loud 拒绝并返回专用业务码 + 转换指引**，
而不是静默跳过（静默跳过会让用户以为「导入了但检索不到」是检索的 bug）。

**设计要点**：PDF 是**静态语料**，天然适合离线批处理；
把解析器放进运行时会让「一个有 bug 的 PDF 解析器」变成一个能拖垮业务服务的组件。

## 5. 「严格限定只答本项目问题」怎么落（不是靠提示词）

**只写在 system prompt 里是无效的** —— 提示词可以被用户话术绕过，也无法解释「为什么拒」，
更无法被测试。本项目落成**三段式确定性的护栏**：

1. **领域判定**（`DomainGuard`，确定性的本地规则/分类）→ 输出 `business` / `standard` / `other`
2. `business`（本项目业务域：七阶段状态机、角色权限、报告、判定规则、操作指引）→ **由本地业务规则/数据确定性作答，不调模型**
3. `standard`（检验检测领域：标准条文、限量值、检测方法）→ 走 GB 检索，**带标准号与出处**回填给模型做组织
4. `other` → **拒答**，话术是「同事口吻 + 给 2~3 条替代建议」，**不是系统的红色报错**

**为什么业务域不调模型**：这类问题的答案本来就是确定性的（「S40 是什么意思」「下一步该做什么」），
让 4B 模型去复述项目规则，既慢又可能编错。**确定性的事交给确定性代码。**

**实测降级矩阵 7 项**（关键：业务域与越界拒答路径**调用模型 0 次**）：
业务域确定性作答 / 越界拒答 / 标准域有命中 / 标准域无命中（诚实说「未在本地标准库找到」，**绝不编造标准号**）/
Ollama 不在线 / 模型超时 / 流中断。

### 两条红线（都用可执行断言固化，不是注释）

- **AI 绝不写入任何业务结论字段**。判定权威永远是 `JudgeEngine`（闭集白名单矩阵）。
  → 固化方式：`AiDomainIsolationTest` 用**反射穷举 `AiAssistantServiceImpl` 的依赖**，
  断言其不持有任何「能写判定链」的 Mapper。「以后有人不小心注入进来」会被测试挡住。
- **禁止 mock 假数据**（本项目既有红线）。检索无命中就说没找到，不编造标准号。
  这是 AI 类功能最容易犯的错，也是最危险的一个 —— 编造出来的 GB 号在检验机构是**资质事故**。

## 6. 前端：不引 Markdown 库，改「结构化回答」

后端直接返回结构化对象：

```
{ answer, citations:[{ stdNo, clause, snippet, sourceFile, score }], refused, domain, online, ... }
```

比「返回 Markdown 字符串 + 前端渲染」更好的三点：
1. **引用卡片天然强制出处**：`citations` 是结构化的，UI 不可能「忘了标标准号」。
2. **零新增依赖**（不用引 markdown 渲染器 + 安全过滤）。
3. **可审计**：`ai_message.citations_json` 直接存结构化引用快照，
   事后能证明「这次回答引用了哪一版标准的哪一条」。

## 7. AI 必须是业务系统的「旁路」

LIMS 是生产系统，AI 是增强。硬性设计：

- Ollama 离线 / 超时 / 非 200 / 流中断 → `/api/ai/**` 返回**明确的降级态 + 可操作的修复指引**
  （指向 `ai/scripts/start-ollama.ps1`），**业务接口零影响**。
- 独立的健康检查端点 `GET /api/ai/status`，供前端显示状态点。
- 「AI 不可用」**不能用错误告警表达**：它是「服务未启动」这一正常状态，
  红色报错会让用户判定整个系统坏了（本项目既有教训：用错误告警表达权限不足，用户原话是「不需要这样报错显示啊」）。

## 8. 可复用结论（给同类项目）

1. **先验证离线仓，再设计**。`spring-ai`/Lucene/PDFBox 在不在，直接决定方案是「引框架」还是「手写 200 行」。
2. **JDK 17 的 `HttpClient` + Spring 的 `SseEmitter` 足以做本地 LLM 接入**，
   不需要 WebFlux、不需要 AI 框架。少一层抽象，多一分对超时/中断的掌控。
3. **MySQL ngram 是中文检索的零依赖答案**，但必须知道它的三个坑（单字丢弃 / 改错参数 / MATCH 列必须与索引列一致）。
4. **护栏要写成代码和测试，不要写成提示词**。要能被测试，才能被信任。
5. **AI 的「辅助判断」在资质类系统里只能是「建议性引用」**：必须有出处、必须与系统判定在视觉上区分、必须不写业务字段。
6. **索引是派生数据，不是业务留档** —— 明确区分这两者，否则会被「禁止删数据」的原则绑住手脚。
7. **大文件下载步骤要假设会失败**：多镜像 + 手动兜底 + 状态自检。
