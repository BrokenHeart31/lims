# LIMS UI 公共组件体系与逐页迁移方法

## 适用范围

适用于 Vue 3 + TypeScript + Element Plus 的 LIMS 类后台系统，在不改变 API、权限、Pinia 数据结构和业务状态机的前提下，统一页面的视觉层、加载态、空态、筛选栏和高风险确认交互。

## 1. 先建立稳定的视觉层级

页面不要依赖大量阴影或玻璃模糊来制造层次。当前项目采用五层实色阶梯：

- page：`#080C10`
- sidebar：`#0D1218`
- header：`#10161D`
- card：`#131A22`
- elevated：`#1B2530`

普通卡片使用 card 层、细边框、无阴影；弹窗、抽屉、下拉面板才使用 elevated 层和阴影。品牌色统一为 `#18D6C5`，成功/警告/危险/紫色分别表达业务状态。

## 2. 公共组件职责边界

| 组件 | 负责 | 不负责 |
|---|---|---|
| `PageHeader` | 页面标题、说明、面包屑与操作区 | 查询参数、权限判断 |
| `AppCard` | 面板层级、边框、内边距和可选 hover | 业务数据请求 |
| `StatCard` | KPI 数值、图标、提示文字 | 统计口径计算 |
| `StatusBadge` | 状态/结论的颜色语义 | 前端重新计算结论 |
| `DataFilter` | 筛选栏响应式布局与 actions 插槽 | 查询和重置行为 |
| `DataTable` | loading、empty、分页外壳 | 表格列和业务行操作 |
| `AppEmpty` / `AppLoading` / `AppSkeleton` | 空态、错误态、加载态（**加载中优先骨架屏**） | 请求重试策略 |
| `askConfirm` | 删除、退回、审核、签发等高风险确认 | 后端权限与状态校验 |

页面保留原有 API 调用和业务函数，只将结构与视觉责任下沉到公共组件。

## 3. 业务异常必须整行可见

结果录入页的明细表使用 Element Plus `row-class-name`，但分类只消费后端已经产出的结论：

- `conclusion == null`：未录入，紫色；
- `conclusion == 3`：待判定，橙色；
- `conclusion == 2`：不合格，红色；
- `conclusion == 1`：不额外染色。

不要在前端根据数值再次推断合格/不合格；前端仅展示判定引擎结果，避免与后端口径漂移。

## 4. 审核台 KPI 的统计边界

审核/签发列表是分页接口。当前 KPI 采用可审计的双边界：

- 待审核/待签发：使用服务端 `total`，代表当前筛选条件下的全量待办；
- 异常样品、异常项、不合格：仅统计当前页 `records`，标签明确写「本页」，不把一页数据伪装成全库统计。

如果未来需要全量异常 KPI，应新增后端聚合接口，不能从分页结果反推。

## 5. 迁移顺序

1. 先盘点页面和业务红线；
2. 统一 tokens 和 Element Plus 覆盖；
3. 先改 Layout，再抽公共组件；
4. 先迁移报告审核、结果录入、Dashboard 等高风险/高频页面；
5. 再迁移系统管理、基础数据、查询页；
6. 最后统一分辨率、横向滚动、Console Error 和空态/错误态。

每一批改动后必须执行 `npm run lint`、`vue-tsc --noEmit` 和 Vite build。构建目录若受沙箱保护，使用新的 `LIMS_BUILD_OUTDIR`，避免删除既有目录。

## 可复用结论

公共组件的成功标准不是页面代码更短，而是「业务逻辑留在页面、视觉和状态外壳集中治理」。对于分页 KPI、判定结论和权限确认，必须把统计范围、数据来源和安全边界写在代码注释与知识库中，防止后续迁移时出现看似漂亮但语义错误的 UI。
