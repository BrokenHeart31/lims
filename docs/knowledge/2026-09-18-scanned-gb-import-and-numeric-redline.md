# 扫描版 GB 标准的 OCR 导入通道 + 「数值类问答」红线设计

> 日期：2026-09-18　实施：GLM
> 背景：用户提供 `GB2763-2021-ys.pdf`（67MB）要求「能自动查询对应标准、辅助判断」。
> 实测发现它是**纯扫描件**，并顺带炸出一个**原设计没预料到的危险点**——模型会自信地给出
> 「看起来完全合理」的错误限量值。两件事都成了本次设计的核心约束。
> 相关：`docs/design/2026-09-18-arch-ai-flow-assistant.md`、`ai/scripts/prepare-standards.py`

---

## 1. 先判定：这份 PDF 到底有没有文字层（不要直接上 OCR）

拿到 PDF 别急着 OCR。**先判形态**，因为两条路的成本差一个数量级：

| 形态 | 判定特征 | 处置 |
|---|---|---|
| 有文字层 | 页面有 `/Font`，`extract_text()` 有输出 | 直接抽文本（秒级） |
| 中文 CID 字体缺 ToUnicode | 有 `/Font` 但 `extract_text()` 为空 | 换抽取器/字体修复，**不必 OCR** |
| **纯扫描件** | **无 `/Font`**，页面资源只有一张大图 | **必须 OCR** |

**判定脚本要点**（`pypdf`）：
- `len(PdfReader(p).pages)` 拿页数；`page.extract_text()` 在若干抽样页上统计字符数
- 解剖 `page["/Resources"]`：看 `/Font` 是否存在；遍历 `/XObject`，`/Subtype == "/Image"` 的记录
  `(/Width, /Height, /Filter, /ColorSpace)`

**本案实测结论**：
```
422 页 / 67MB / 未加密
每页 content stream 仅 107 字节；无 /Font；/XObject 只有一个：
  /Im1  /Image  1240×1753  /DCTDecode  /DeviceRGB
在 p0,p1,p2,p10,p50,p100,p421 共 7 页抽样 → extract_text() 合计 0 个字符
```
→ 每页就是一张 **1240×1753 的 JPEG**（≈ A4@150DPI）的纯扫描件。

> **教训**：`extract_text()` 返回空**不等于**「文件损坏/加密」，也不等于「没有文字」。
> 必须看页面资源才能区分「扫描件」与「字体缺 ToUnicode」——这两者的解法完全不同，
> 判错的代价是把一个可以秒级完成的事拿去做几小时的 OCR。

## 2. OCR 引擎选型：RapidOCR（离线、无外部二进制）

| 候选 | 裁决 |
|---|---|
| **`rapidocr-onnxruntime`** | ✅ **选定**。纯 pip 安装、内置 PP-OCR 中文模型、仅依赖 onnxruntime（CPU 可跑）、**不需要 Tesseract 之类的系统级二进制** |
| PaddleOCR | ❌ 需 paddlepaddle（数百 MB，安装链长、易失败） |
| EasyOCR | ❌ 需 PyTorch（GB 级依赖），对本用途过重 |
| Tesseract | ❌ 需额外安装系统二进制 + 中文语言包，部署面变大 |
| Windows.Media.Ocr | ❌ 中文精度不足，且绑定 Windows API |

**实测**：`pip install rapidocr-onnxruntime` 成功；`from rapidocr_onnxruntime import RapidOCR` 可用。
⚠️ **入参只接受 `str / bytes / pathlib.Path / np.ndarray`，不接受 `PIL.Image`**——
传 `PIL.JpegImagePlugin.JpegImageFile` 会抛 `LoadImageError`。
页内嵌图取 `page.images[0].data`（`bytes`）直接喂最省事。

## 3. ★★ 并发陷阱：4 个 worker 比 1 个还慢 26%

这是本次最有价值的一条踩坑，**任何「多进程 + onnxruntime/OpenMP」的场景都会踩**。

**现象**：

| 配置 | 吞吐 | 422 页外推 |
|---|---|---|
| 单进程（未钉线程） | **8.4 秒/页 = 7.14 页/分钟** | ≈ 59 分钟 |
| `workers=4`（未钉线程） | 62 页 / 11.73 分钟 = **5.29 页/分钟** | ≈ **80 分钟** |

**4 并发只有单进程的 74%** —— 加并发是负收益，比串行还慢。

**根因**：`onnxruntime` 的 intra-op 线程数与 OpenMP 线程数**默认取逻辑核数**。本机 32 核，
于是 4 个 worker × 32 线程 = **128 个线程抢 32 个核**：上下文切换 + 缓存抖动吃掉的时间
超过了并行省下的时间。**进程数涨了，但总线程数没被约束**。

**修法**：让 `workers × 每-worker线程数 ≲ 核数`，并把每-worker 线程钉死：
1. 环境变量 `OMP_NUM_THREADS` / `OPENBLAS_NUM_THREADS` / `MKL_NUM_THREADS` 设为
   `核数 / workers`（本案建议 `workers=4` × 6 线程 = 24，留 8 核给同机 Ollama）；
2. ⚠️ **必须在 `import onnxruntime` / 构造引擎之前设置**——线程池在导入期就确定，事后设置无效；
3. 多进程（尤其是 Windows `spawn` 启动方式）下，**父进程的 `os.environ` 不保证被 worker 继承**，
   稳妥做法是在 **worker 的初始化函数里显式设置后 import**。

**代价对比**：钉对线程后 4 并发接近线性（≈15 分钟），钉错则比单进程更慢。
→ **不要只看 `workers` 数字，要看「总线程数 vs 核数」这个比值。**

> 附带提醒：给同机跑 LLM 推理留核。本案 32 核里给 Ollama 留 8 核（模型解码 1~2 核满载即可），
> 否则会出现「OCR 跑起来之后模型推理慢到不可用」这种极难定位的「性能问题」。

## 4. OCR 的精度边界：正文可信、**数值不可信**

实测抽样（同一份文件）：

| 页 | 内容 | 识别结果 | 评价 |
|---|---|---|---|
| p0 封面 | `ICS 65.100 G 25 中华人民共和国国家标准 GB 2763—2021 代替GB2763—2019 食品安全国家标准 食品中农药最大残留限量 …` | 完全正确 | ✅ 可直接用 |
| p5 目录 | `氟节胺lumetralin 4. 171 133 …` | 正文准确；编号被插入空格；`flumetralin` 误作 `lumetralin` | ⚠️ 影响很小 |
| p120 限量表 | `最**人**残留限量，mg/kg … 牛肝 0. 05` | **「最 大」→「最 人」**；`0.05` → `0. 05` | ❌ **数值不可信** |

**结论（本项目的硬约束）**：OCR 文本**只用于条文引用与定位**（条款号、标题、正文表述、适用食品类别），
**数值与判定绝不取 OCR 结果**。150 DPI 的中文扫描件出现「大→人」这类形近字错误是必然的，
而这类错字一旦落在**限量值**上，后果是检验机构资质事故级别。

## 5. ★★ 真正的杀手：模型会「自信地给出合理但错误的限量值」

这条是本次最意外的发现，也是最危险的。

**实验**：问 `qwen3:4b-instruct`「GB 2763-2021 里毒死蜱在黄瓜上的限量是多少？」

**模型回答**（3.6 秒、74 tok/s、`think=false` 生效、思考内容 0 字）：

> 毒死蜱（Chlorpyrifos）在黄瓜上的最大残留限量为 **0.05 mg/kg**。该限量适用于新鲜黄瓜…

**去库里查「毒死蜱」的真实数据**：

```
item_name  basis_code     std_value  unit    judge_type
毒死蜱      GB 2763-2021   0.05       mg/kg   1
毒死蜱      GB 2763-2021   0.3        mg/kg   1
毒死蜱      GB 2763-2021   0.5        mg/kg   1
毒死蜱      GB 2763-2021   0.7        mg/kg   1
毒死蜱      GB 2763-2021   1          mg/kg   1
毒死蜱      GB 2763-2021   2          mg/kg   1
毒死蜱      GB 2763-2021   3          mg/kg   1
…（共 25+ 行）
```

**根因**：`product_lib_item` 的列是
`id, product_lib_id, item_order, item_name, unit, basis_code, methods, std_value, judge_type, is_reference, lower_limit, method_note, 审计四字段, deleted`
—— **没有「食品类别 / 食品名称」列**。限量是挂在 `product_lib_id`（具体产品）上的，
所以同一农药在不同产品下限量不同；而 GB 2763 原文的结构恰恰是「食品类别/名称 × 农药」的二维表。

**所以模型答的 `0.05` 只是「某个产品的值」**，它没有任何依据知道这个值适不适用于黄瓜。
它这次「答对」纯属巧合（0.05 确实存在于库中某个产品行上）——换个项目或作物就会自信地答错。
**而错误答案的形式与正确答案完全一样，用户无法分辨。** 这比「答不出来」危险得多。

### 由此确立的三条设计约束

1. **数值类回答的唯一合法通路是「样品上下文 → `sample_item` 快照」。**
   快照里有该样品**适用的** `std_value` / `unit` / `lower_limit` / `basis_code` / `judge_type`。
   → 问「**这个样品**的毒死蜱限量是多少」：可以给值，并可溯源到 `basis_code`。
   → 问「毒死蜱在黄瓜上的限量」（**无条件上下文**）：按 `item_name` 检索会得到 25 个互斥值，
     **无法唯一定位 → 不得给出单一数值**。正确做法是说明「该标准下毒死蜱有多档限量（依食品类别而定）」，
     附标准原文引用，并引导用户到具体样品/具体食品类别的入口。
2. **`ValueAnchorAssembler` 的依赖集不得包含 `gb_*` / `GbRetriever` / `JudgeEngine`**（用单测锁死）。
   把「数值不取自 OCR 文本」从一个流程约定，变成一条**测试期不可绕过的边界**。
3. **任何涉及数值的回复必须携带可追溯的结构化来源**（`citations`），来源只能是「样品快照」或「标准原文片段」；
   两者都取不到时，回答「无法确认，请查看样品明细 / 标准原文」，**而不是给一个数**。

### 顺带印证的另一条：模型不认识项目术语

问「S40 是什么意思？」（本系统自己的状态码）→ 模型答的是**三星 S40 手机**。

→ 这直接说明：**业务域与状态机类问题必须由本地确定性规则回答，绝不能交给小模型自由发挥**。
「事实层（后端确定性装配）/ 措辞层（模型只润色不改事实）」的分离不是洁癖，是可靠性的前提。
另外从可复现性看：同一问题两次调用得到不同表述，在检验机构场景里本身就不可接受。

## 6. 推理性能实测（`qwen3:4b-instruct` / CPU）

| 指标 | 实测值 |
|---|---|
| 首答耗时 | **3.6 秒**（问题长度中等） |
| 解码速度 | **约 74 tok/s** |
| `think=false` | ✅ 生效（返回的 `thinking` 字段为 **0 字**，正文未被思考内容污染） |
| 模型规格 | Q4_K_M / 4.0B / 2.5GB / 上下文标称 262144（实用取 4K~32K） |

结论：4B 在这台机器上**交互可用**（推理不是瓶颈，瓶颈在检索与装配）。
但**绝不能因此就让它去回答事实类问题**——快不等于对。

## 7. 「存量库启用」：两个必须避开的破坏性陷阱

本案交付的建表脚本从未在活库执行过（因为实施阶段禁止跑数据库写操作，只在临时库验证过 DDL），
于是「把脚本应用到活库」本身成了一个必须设计的步骤。两个坑：

**坑 ①：`db/init/NN_*.sql` 惯用 `DROP TABLE IF EXISTS` 开头**（为「全新部署」设计，本身没错）。
但**一旦库里已有数据（比如刚导完几百兆的标准库），再跑一次就会把数据清空**。
→ 存量库启用必须是「**只建缺失的表**」：先查 `information_schema.tables` 判定，缺失才建；
或另写 `CREATE TABLE IF NOT EXISTS` 的存量库版本。**并在脚本里写显警告注释**——
这是最容易被后续维护者误触的破坏性操作。

**坑 ②：整体种子脚本通常不可重跑**。`db/seed/01_rbac_seed.sql` 用**显式 id** 插入
（`INSERT INTO sys_menu (id, ...) VALUES (121, ...)`），且**没有** `ON DUPLICATE KEY UPDATE` /
`INSERT IGNORE` / `REPLACE` → 整体重跑到第一行已存在的 id 就主键冲突。
→ 增量权限行必须单独抽成**幂等**脚本应用。

**判据**：`db/init/` 与 `db/migrations/` 的分工不只是「建表 vs 改表」，
更是「**面向空库 vs 面向存量库**」——存量库路径上的每一步都必须幂等且不破坏数据。

## 8. 可复用结论

1. **先判 PDF 形态再决定要不要 OCR**（有 `/Font` 吗？`extract_text()` 空不空？页面是不是一张大图？）。
2. **OCR 选 RapidOCR**：离线、无系统二进制、中文够用。注意它不收 `PIL.Image`。
3. **多进程 + onnxruntime 必须钉线程**，否则 `workers` 越大越慢（本案 4 worker 比 1 worker 慢 26%）。
   看的是「总线程数 vs 核数」，不是 `workers` 数字；记得给同机 LLM 推理留核。
4. **OCR 文本只做引用与定位，数值一律不取 OCR**（实测「最 大」→「最 人」）。
5. **绝不让模型凭记忆答数值**。数值只能来自「该对象自己的快照」，且必须带结构化来源；
   取不到就说取不到。**错误答案与正确答案长得一模一样，这是最危险的地方。**
6. **业务术语/状态机类问题交给确定性代码**，模型只润色措辞（4B 会把 `S40` 答成三星手机）。
7. **存量库启用脚本必须只建缺失的表 + 幂等**，否则一次误跑清空知识库。
