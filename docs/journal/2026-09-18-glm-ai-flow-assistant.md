## 2. 💡 心得与判断

### 2.1 「拿到 PDF 先别 OCR」——先判形态，成本差一个数量级

用户给的 67MB PDF，我先做的是**判形态**而不是直接跑 OCR：读 `page["/Resources"]`。
结论是**每页只有一张 1240×1753 的 JPEG、无 `/Font`、7 个抽样页 `extract_text()` 合计 0 字符** → 纯扫描件，必须 OCR。

但判形态的价值不止于「要不要 OCR」：**`extract_text()` 返回空有三种完全不同的成因**
（加密 / 中文 CID 字体缺 ToUnicode / 真的没有文字层），**后两者的解法天差地别**。
判错的代价是把一个秒级可完成的事拿去做几小时 OCR。故 `prepare-standards.py` 里也保留了这个探测，
并在「无文字层」时主动提示两条路（换文本版 PDF / 走 `--ocr`）。

### 2.2 ★ 加并发反而更慢：线程超订的两次实证

第一版 `workers=4`：**5.29 页/分钟**，而我实测单进程是 **7.14 页/分钟**——4 并发只有单进程的 74%。
第二版更糟：**162 页后完全停滞 20 分钟以上，CPU 满速却零产出**（活锁）。

**根因**：`onnxruntime` / OpenMP 的线程数**默认取逻辑核数**。本机 32 核 ⇒ 4 worker × 32 = **128 线程抢 32 核**。
CPU 时间取样证实了这一点：每个 worker 在 25 秒墙钟里吃掉 4~5 分钟 CPU 时间（≈12 个核）。

**修法**：令 `workers × 每-worker线程数 ≲ 核数 − 预留`。钉成 **4 × 7 = 28**（给同机 Ollama 留 4+ 核）。
且必须在 **import onnxruntime 之前**设置（`_pin_threads` 在 worker 初始化函数里显式设 `OMP/OPENBLAS/MKL_NUM_THREADS`）。

**连带教训**：那次活锁把整台机器占满，连我的 shell 都开始报 `fork: Resource temporarily unavailable`。
「什么都变慢但不知道为什么」是最难查的一类问题，**多进程 + 线性代数库必须默认钉线程**。

### 2.3 断点续跑的验证点是「跳过了多少」，不是「跑完了没有」

重启 OCR 后日志首行是：
`[ocr] GB-2763-2021：共 422 页，本次待 OCR 260 页（已续跑 162，文字层 0，无图像失败 0）`
—— **这行才是「断点续跑真的работает」的证据**（162 页被跳过、只补剩余 260 页）。
如果只看「最后跑完了」，无法区分「续跑」与「从头重跑一遍」。另外我顺手确认了恢复逻辑**以页文件存在性为准**、
不是以 `progress.json` 的计数为准（否则 `.tmp` 残留会让它重做已完成的页）。

### 2.4 ★★ 本项目最危险的一类错误：「看起来完全合理的错误答案」

问 `qwen3:4b-instruct`「GB 2763-2021 里毒死蜱在黄瓜上的限量是多少？」，它答：

> 毒死蜱（Chlorpyrifos）在黄瓜上的最大残留限量为 **0.05 mg/kg**。该限量适用于新鲜黄瓜…

去库里查：`毒死蜱` 有 **25 条不同限量**（0.05/0.3/0.5/0.7/1/2/3 mg/kg）——因为 `product_lib_item`
**没有食品类别列**，限量挂在「产品」上，而 GB 2763 原文的结构是「食品类别/名称 × 农药」的二维表。
后来检索出的原文里，**黄瓜对应的是 0.02**——**模型答错了**。

**关键认识**：它错得**和正确答案长得一模一样**，用户无法分辨；这比「答不出来」危险得多。
所以「AI 不写判定字段」这条既有红线还不够，必须再加一条：**数值类回答不得来自模型记忆，只能来自该对象自己的快照**。

**反讽的是**：`product_lib_item` 缺的正是「食品类别」这个维度，而那份扫描件原文里**有**这张二维表。
→ OCR 导入因此有了独立价值：它不只是「为引用而引用」，而是补上了数值库缺失的归类维度。

### 2.5 事实层 / 措辞层分离不是洁癖，是可靠性的前提

同一批实测里，问「**S40 是什么意思？**」（本系统自己的状态码），模型答的是**三星 S40 手机**。

→ 印证了 PRD 的 TF 裁决：**业务域与状态机类问题必须由本地确定性规则回答**。
落地后「S40 是什么意思」变成 **16ms 秒回**且口吻正确，**调用模型 0 次**。
确定性的事交给确定性代码：既快，又不会「同一个问题两次答案不同」。

### 2.6 Bug 修复的三个判断

**① `@Transactional` 里调 `@Async` ＝ 异步线程读不到未提交数据。**
导入任务永远停在「待处理」，日志里只有一条不起眼的 WARN「导入任务不存在：1」。
判据：`insert` 与 `worker.run` 同一方法内，且方法上有 `@Transactional` → 必然竞态。
修法：`TransactionSynchronizationManager.registerSynchronization(... afterCommit ...)`。

**② BOOLEAN 模式下「不含空格的整句中文」必然 0 命中。**
我的探针给出决定性对比：同一整句 `+整句`=0 条 / `整句`=0 条 / **自然语言模式=844 条**；
而两词空格分隔（`毒死蜱 黄瓜`）在布尔下=138 条。
→ 结论：布尔层对「已分词」输入有效，**整句必须走自然语言模式**。补第三级兜底（AND → OR → 自然语言）。

**③ 给 4B 模型写提示词，「禁止 X」会诱发它复述 X。**
第一版提示词写「⚠️ **禁止输出任何具体限值数字**…不得凭记忆或从条款片段中摘取数字」，
模型输出变成：「⚠️ 但请注意：…**不得凭记忆或从条款片段中摘取数字**。✅ 正确回答应为：…」
——**它把规则当内容复述出来了**，而且先给了数字再收回，自相矛盾。

修法两条：① 显式要求「只输出最终答复，不要出现『根据要求』『正确回答应为』这类元话语」；
② **给一个作答模板**（4B 模型照结构写比「遵守规则」可靠得多）。

改完后又出现**矫枉过正**：模型因为「不能写数值」就一律回「标准条款未覆盖」。
→ 再补一条边界：**「条款主题无关」才叫未覆盖，「不能写数值」不叫未覆盖**。改完 2/3 问法正常作答。

**这轮提示词改了三版**，每版都是「实测 → 发现新问题 → 收窄边界」。**小模型的提示词不能靠推理，只能靠实测。**

# 2026-09-18 追加 —— 用户实测反馈的三个缺陷（AI 助手「卡在正在生成」）

## 1. 本轮目标

## 2. 实际做法（按排查顺序）

### 2.1 先取证，不猜

- 后端日志：`AuthorizationFilter.doFilter(AuthorizationFilter.java:98)` 抛 **AccessDeniedException**，
  且报 `Unable to handle the Spring Security Exception because the response is already committed`。
- `curl -N` 复现：**帧收齐了（refs/token/done 都在），但退出码 = 18**（`CURLE_PARTIAL_FILE`）。
  → 关键判据：**不能只看「帧到了」，要看退出码**；服务端发全了、连接仍可能被 RST。
- 时间序列比对：`ai_message` **insert 成功之后 27ms** 才报错 ⇒ 说明错误发生在**流结束时**，不是请求开始。

### 2.2 三个独立缺陷（详见 `docs/knowledge/2026-09-18-sse-async-vue-reactivity-ngram-routing.md`）

| # | 缺陷 | 严重度 | 修法 |
|---|---|---|---|
| 1 | `SseEmitter` 完成触发 ASYNC 派发 → JWT 过滤器默认跳过 → 上下文匿名 → 鉴权失败 → 响应已提交无法转错误 → **连接被掐断** | P0 | `SecurityConfig` 放行 `DispatcherType.ASYNC/ERROR` + `shouldNotFilterAsyncDispatch()→false` |
| 2 | **前端改「push 进 `ref([])` 的裸对象」不触发视图更新** —— 这才是「重开面板才看到答案」的真因 | P0 | push 后**取回数组里的响应式代理**再改 |
| 3 | 检索路由：整句走 BOOLEAN ⇒ 短语语义 0 命中；噪声词（`GB`/`2763-2021`）OR 兜底制造 **968 条假命中**，正确块 `score=0` 未入候选 | P1 | 整句走自然语言模式；噪声词从布尔层剔除；`clause_title` 建 ngram 索引并作为第一排序键 |

### 2.3 前端兜底（防止同类问题再出现「永久生成中」）

`utils/aiStream.ts` 增加：

- **静默超时**（30s 无任何字节 → 主动 abort 并报错，附「计时被 token 重置」的说明，长回答不会被误杀）；
- **`onIncomplete`**：连接正常结束但**始终没有 `done` 帧** → 显式回调，让 UI 一定收敛；
- 内部 `AbortController` 与调用方 signal 串联，并区分「用户主动停止」与「超时」。

> 判据：原来的实现里，`reader.read()` 一旦挂住，连 `finally` 都执行不到 —— 所以「store 有 finally 兜底」并不能保证界面不卡。

### 2.4 数据侧：重建 GB 索引

切块/标题规则改完必须重建索引才生效。走设计内的物理重建路径
（`DELETE /api/ai/kb/documents/{id}` → `POST /api/ai/kb/import/scan`）。
重建前先确认脚本**不是** `db/init/10/11`（那两个开头是 `DROP TABLE`，会清库）。

## 3. 💡 心得与判断

1. **「done 帧到了」不等于「流正常结束」**——`curl` 退出码比帧内容更能说明问题（18 vs 0）。
2. **`store` 里写了 `finally` 也不代表界面不会卡**：卡在 `await reader.read()` 时，`finally` 根本轮不到执行。
   前端对「不可信网络」必须有**主动超时**，不能只依赖后端关闭连接。
3. **「重开组件就正常」几乎可以确诊为响应式失效**（重新挂载会重新求值），而不是后端问题。
   验证手段：用 `@vue/reactivity` 的 `effect` 打计数，比读代码快且不容争辩。
4. **检索质量要分层看：召回 ≠ 排序**。本次正确块是「压根没进候选集」（召回失败），
   光调排序无解；必须先把**噪声词**从查询里拿掉、把**整句**交给正确的模式（自然语言）。
5. **OCR 国标的版式必须先归一**：`4. 121` + 名称分列两行，这类版式问题会让「条款号 ↔ 内容」整段错位，
   而错误归属在合规系统里**比没有归属更危险**，必须修在入库之前。
