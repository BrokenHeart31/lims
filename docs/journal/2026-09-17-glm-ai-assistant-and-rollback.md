### 2.2 设计前先验证「约束」，而不是先画图

这是本轮最有价值的一个动作。本项目 Maven 是**离线本地仓**，所以任何「引个库就行了」的方案都要先证伪：

| 实测项 | 命令/方式 | 结果 |
|---|---|---|
| 离线仓有没有 AI 框架 | `ls ~/.m2/repository/org/springframework/ai` | **有** `spring-ai-* 1.0.0-M6`（M 里程碑） |
| 有没有搜索库 | `ls ~/.m2/repository/org/apache/lucene` | **没有** |
| 有没有 PDF 解析库 | `ls .../pdfbox`、`.../tika` | **都没有** |
| 有没有 HTML 解析库 | `ls .../org/jsoup/jsoup` | **有 1.18.3** |
| MySQL 中文检索能力 | `SHOW VARIABLES LIKE 'ngram%'` + `information_schema.PLUGINS` | **ngram ACTIVE，`ngram_token_size=2`** |

**结论**：AI 接入用 **JDK17 自带 `HttpClient`**（零依赖），检索用 **MySQL ngram 全文索引**（零依赖），
唯一新增依赖是 `jsoup`（无 JDK 内置替代）。

**如果跳过这一步**：很可能写出一个「引 Lucene + spring-ai」的方案，然后在编译期发现拉不到包，全部返工。

## 3. 💡 心得与判断

### 3.1 判定「逆向动作」必须按语义分类，不是按方向分类

既有状态机有 `VALID`（正向）与 `RETURN`（审核退回）两张白名单，类注释明确写「正向与退回不得合并」。
新需求要加「回退」时，最省事的做法是把 `S20→S10`、`S30→S20` 等边塞进 `RETURN`（都是往回走嘛）。

**判断：不能。** 两者在四个维度上完全不同：语义（业务否定 vs 纠错）、触发者（下游角色 vs 操作者本人）、
**数据处置**（不动 vs 必须失效下游）、可撤销性（否 vs 是）。若合并，`assertTransition(S60,S50)` 与
`assertRollback(S60,S50)` 会变成同一件事，调用方无法表达意图，单测也无法固化不变式。

→ 落为**第三条独立白名单 `ROLLBACK`**。这个判断后来在实现里被证明是对的：`RollbackServiceImpl` 需要
「失效下游 + 留档 + 可恢复」一整套逻辑，而这些在 `RETURN` 里**一个都不需要**。

### 3.2 红线的正确落点是「白名单里没有这条边」，不是「界面上藏按钮」

用户要「任意历史节点都可回退」，而本系统里 **S80 已签发（报告已对外生效，带 CMA/CATL 标识）、
S90 已出报告（数据已上报省平台）**。这两步在资质意义上不可能「回退」。

**判断**：`ROLLBACK` 白名单里**根本不存在 S80/S90 的出边**。如果只在 UI 上禁用按钮，一行 curl 就绕过去了；
放在白名单里，任何新写的 Service 都绕不过。

同时给了出口：`report_void`（作废/召回标记动作，**只写标记不改 status**），既满足 PRD T4，又不让「不可回退」变成「没有办法」。

### 3.3 「任意历史节点」的落地取舍：可跨级**看**，不可跨级**退**

**判断**：跨级回退（S70 一步退 S40）看起来更「方便」，但它要在一个调用里串起 3 套处置
（动结果 / 动分配 / 动分解），而**失败时没有原子回滚的落点**——数据层已经动了。
逐级退让每步可验证、每步一条流水、出错能精确定位。`sample_status_log` 让「任意历史节点」在**查看层**成立，用户诉求已满足。

### 3.4 审计系统里「回退 ≠ 删除」

三种候选（快照还原 / 反向补偿 / 版本化留档），**排除前两者**：

- **快照还原**：整表覆盖回去 → 会让「这一行的这段历史从未存在过」成为事实，事后无法回答「当时是谁录了什么」。
  且与既有「覆盖式 upsert + 审计四字段」形成两套真相。
- **反向补偿**：逆操作要逐个操作手写，**漏一个就是静默的数据损坏**；且逆操作是代码，升级后语义漂移，
  历史回退行为不可复现。

→ 采纳**版本化留档**：回退只做「状态逆流 + 置失效 + 留档」，主表只增不改。

### 3.5 一个意外的收获：给「覆盖式保存」补上了 ALCOA+ 缺口

为了让「回退到重新录入」能回答「用户看到的是哪个值、旧值还能不能取证」，不得不给
`ResultServiceImpl.upsertResult`（覆盖式 upsert，**旧 `test_value` 被直接覆盖**）也加**保存前修订留档**。

**这个留档不只在回退时触发——正常重复保存也会留档。** 于是顺带补上了一个既有的 ALCOA+ 缺口：
此前「检验员改了数值再保存」旧原始值就永久消失了。

**判断依据**：ALCOA+ 的 "Original" 要求原始记录可追溯。这是本项目此前没被识别的问题。

### 3.6 AI 在资质类系统里的定位：只能是「建议性引用」

产品经理在 PRD T3 里把它写成了红线，架构师把它落成了结构：

- AI 输出**必须带标准号 + 条款出处**（结构化 `citations`，UI 渲染成引用卡片 → 「忘了标出处」在结构上不可能）。
- AI **绝不写入任何业务结论字段**。判定权威永远是 `JudgeEngine`（闭集白名单矩阵）。
- UI 必须显式标注「**AI 建议，仅供参考；判定以系统规则为准**」，与系统判定结论在视觉上不可混淆。

**工程师的加固值得记一笔**：写了 `AiDomainIsolationTest`，用**反射穷举 `AiAssistantServiceImpl` 的依赖**，
断言它不持有任何「能写判定链」的 Mapper。这把一条注释承诺变成了**可执行断言**——
「以后有人不小心注入进来」会被测试挡住。这个模式我会在项目知识库里推广。

### 3.7 「严格限定只答本项目问题」不能只写在提示词里

**判断**：只写 system prompt 是无效的——可被话术绕过、无法解释「为什么拒」、无法被测试。

→ 落成三段式**确定性**护栏：`business`（本项目业务域）→ **由本地业务规则确定性作答，不调模型**；
`standard`（检验检测领域）→ 走 GB 检索后回填；`other` → 拒答（同事口吻 + 2~3 条替代建议）。

**为什么业务域不调模型**：「S40 是什么意思」「下一步该做什么」的答案本来就是确定性的，
让 4B 模型复述项目规则既慢又可能编错。**确定性的事交给确定性代码。**

## 4. ⚠️ 踩坑记录

### 坑 1（实施环境）：沙箱代理对大文件返回 502，7 条镜像路径全挂

**现象**：`curl -L https://github.com/ollama/ollama/releases/latest/download/ollama-windows-amd64.zip` → `HTTP 502`。
**根因**：实施环境的代理拦截了 Release 大文件（`ollama.com/download/*.zip` 307 跳 GitHub 后同样 502）。
**排查过程**：依次实测 7 条路径——GitHub 直连 / `ghfast.top` / `gh-proxy.com` / `ghproxy.net` / `gh.llkk.cc` /
`hf-mirror.com` / `modelscope` API。其中 `ghfast.top`、`gh-proxy.com`、`modelscope`、`hf-mirror` 的 **HEAD 探测返回 200**，
但真实 GET 全部失败（`HTTP=000`）。**教训：HEAD 探测通过 ≠ 能下载**（与项目既有的
「`push --dry-run` 不能用来探路」是同一类错误——握手成功不代表数据通道可用）。
**处理**：交付形态改为「一键部署脚本（多镜像回退 + 手动兜底）+ 显式标注真实推理未验证」。
**这条必须写进交付说明**：否则用户会以为「AI 功能已经跑通了」，实际只是「代码写好了」。

### 坑 2（MySQL ngram）：三个行为陷阱（工程师实测撞出）

1. **单字检索词被直接丢弃**：`ngram_token_size=2` ⇒ 检索词长度 < 2 时**恒为空**。
   而检验项目名里单字很常见（重金属项目名多为单字）→ 必须做最小长度校验/词扩展。
2. **调 `innodb_ft_min_token_size` 无效**：英文全文检索的最小词长参数对 `WITH PARSER ngram` 的索引**不生效**，
   行为由 `ngram_token_size` 决定。调错参数会得出「配置改了但没生效」的错误结论。
3. **`MATCH(...)` 的列清单必须与 `FULLTEXT` 索引列完全一致**，否则直接报 **1191**
   （`Can't find FULLTEXT index matching the column list`）。想联合检索「标准号 + 正文」必须另建覆盖两列的索引，不能临时拼列。

### 坑 3（MyBatis-Plus）：`@TableLogic` 不支持表达式

**现象**：要解决「逻辑删除二次失效撞唯一键」，方案是把 `deleted` 从 0/1 升级为「0 / 行自身 id」。
**实测**：MP 的 `@TableLogic` 与 `logic-delete-value` **只支持固定字面量**，无法表达「置为行自身 id」。
**处理**：全局 `logic-delete-value: 1` **保留**（只作用于读写过滤 `WHERE deleted = 0`，与列类型无关），
但这两张表的**失效写入改走原生 `@Update` SQL**（显式 `set deleted = id`），**禁用 `baseMapper.delete(...)`**。
**⚠️ 连带要求**：必须全仓清理硬编码 `deleted = 1` 判定——新语义下「失效值 ≠ 1」，任何 `eq("deleted", 1)` 都是 bug。

### 坑 4（我自己的）：glob 模式 `*ai*` 误匹配 `main`

**现象**：我用 `find backend/src/main/java -ipath "*ai*"` 判断「AI 类是否已开始产出」，结果匹配到 **234 个文件**
（因为路径里的 `ma**i**n` 含 "ai"）。
**教训**：用模糊 glob 做「进度探针」会给出假信号。**探针要匹配**确定性的**文件名前缀/目录段**（如 `service/ai/*.java`），
不要匹配路径子串。

### 坑 5（判断归属）：mtime 不能用来判断「某改动是否本轮引入」

**现象**：`frontend/src/views/base/tester-method.vue` mtime 是本轮（17:31），且相对 HEAD 有**结构性差异**
（多了一层 `<el-table>` 外壳），看起来像「工程师越界改了业务页」。
**排查**：读 `DataTable.vue` 发现它**自身不渲染 `el-table`**，只有 `<slot :rows="rows">` ——
即它的契约是「由调用方自己提供 `<el-table>`」。而 HEAD 版本里那些**裸 `<el-table-column>` 本来就是坏的**。
→ 工作区那层外壳是**修复**，不是回归。
**教训**：`eslint --fix` 会**整文件重写**，所以「mtime 变了」≠「内容被逻辑修改」；
而「相对 HEAD 有差异」也 ≠「本轮引入」——**本次会话起点的工作区本身就带着一批未提交的历史改动**。
判断改动归属只能靠内容比对，不能靠时间戳。
