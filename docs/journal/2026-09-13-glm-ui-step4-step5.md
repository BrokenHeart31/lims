## 二、实际做法

### 1. 页面业务红线保持不变

没有修改 API 路径、请求参数、权限标识、Pinia 数据结构或样品状态机。结果录入页只把后端返回的结论映射到行级样式：

- 未录入：紫色整行；
- 待判定：橙色整行；
- 不合格：红色整行。

`resultRowClassName()` 通过 `conclusionOf()` 读取实时判定缓存或已落库结论，没有在浏览器重复实现判定规则。

### 2. 报告审核首批迁移

`report/audit.vue` 新增审核台 KPI 行：

- 待审核/待签发使用分页接口的 `total`；
- 异常样品、异常项、不合格仅统计当前页，并在标签中标明「本页」；
- 这样没有把一页记录误报成全库指标。

筛选区迁移到 `DataFilter`，审核通过、退回、签发全部改为 `askConfirm()`，异常项仍必须显式勾选确认后才能审核通过。

### 3. 结果录入首批迁移

`result/index.vue` 的筛选区迁移到 `DataFilter`，保留原查询/重置函数和结果录入业务。明细表继续使用 Element Plus 列结构，只新增 `row-class-name` 和对应的 scoped 深色主题行色。

### 4. 系统与基础数据确认统一

`system/user.vue`、`role.vue`、`menu.vue`、`dept.vue`、`base/tester-method.vue`、`base/product-lib.vue` 移除 `ElMessageBox` 直接依赖，删除动作统一调用 `askConfirm()`。后端保护仍是最终安全边界。

## 四、心得与判断

1. 分页 KPI 必须显式写清统计范围。分页结果能支持「当前页异常」而不能支持全库异常；若业务要全库指标，应该补后端聚合接口。
2. 结果录入前端可以强化视觉优先级，但不能把视觉分类写成新的判定引擎。所有结论仍由后端生成。
3. `DataFilter` 只负责布局和插槽，不接管查询行为，避免公共组件反向耦合具体页面 API。
4. 高风险确认集中到 `askConfirm()` 后，删除、审核、退回和签发的交互语义统一，同时保留页面对具体文案和业务条件的控制。
