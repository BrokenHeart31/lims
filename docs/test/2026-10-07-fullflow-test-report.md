## 二、P0 阻断问题（1 项）

### 🔴 F3 项目分解页 / 任务安排页列表「共 N 条但表体 0 行」——`reserve-selection` 缺 `row-key`

- **页面**：`/item/decompose`（项目分解）、`/assign/index`（任务安排）
- **定位**：
  - `frontend/src/views/item/index.vue:428` 的 `<el-table>` 与 `:435-439` 的 `type="selection"` 列（含 `reserve-selection`），**el-table 无 `row-key`**
  - `frontend/src/views/assign/index.vue:379` 的 `<el-table>` 与 `:384-388`（同样 `reserve-selection` 无 `row-key`）
  - **正确范例**：`frontend/src/views/sample/index.vue:482` 有 `row-key="id"`，该页列表正常
- **复现**：
  1. nj001 登录 → 项目分解页（存在 S20 样品时）：工具栏/分页显示「共 N 条」，`el-table` tbody 渲染 **0 个 tr**；
  2. 任务安排页（存在 S30 样品时）同样「共 2 条 / 共 0 条」；
  3. 浏览器内逐层诊断：API 正常、页面 `tableData=N`、ElTable 内部 `store.states.data=N`，但 ElTableBody 渲染 0 行；`doLayout()`/resize/重赋数据均无效。
- **根因（已 A/B 实测锁定，测试改动已全部还原）**：Element Plus 规定 **`reserve-selection` 必须搭配 `row-key`**，否则异步数据到达后表体不渲染。唯一修复变量就是给 el-table 加 `row-key="id"`。
- **建议改法（GLM，各 1 行）**：
  - `item/index.vue:428` `<el-table :data="tableData" ...>` 增加 `row-key="id"`；
  - `assign/index.vue:379` 同样增加 `row-key="id"`。
- **附带（同一文件的无效用法，建议一并改）**：`item/index.vue:432` 与 `:623`（抽屉表）使用 `height="calc(100vh - 360px)"` / `"calc(100vh - 300px)"`；Element Plus 2.9.3 的表格 height 只认数字/固定像素字符串，**不识别 `calc()`**（源码无 calc 处理）。抽屉表因挂载时已有数据侥幸正常。建议改为数值 `:max-height` 或外层容器 CSS 高度。
- **验收**：两页在有 S20/S30 样品时表体渲染出全部行；翻页/筛选后勾选保留仍生效；`npm run build && npx vue-tsc --noEmit` 通过。

## 三、P1 高优先级问题（4 项）

### 🟠 F1 宽表横向裁切 + 固定操作列半透明「鬼影」穿透

- **页面**：监抽任务、样品登记（实测内部表宽 1070/1316px > 容器约 722/744px）；结果录入抽屉、审核抽屉同样复现（右侧「单项结论/检验方法/检验员」列被裁切，无横向滚动条）。
- **定位**：`frontend/src/components/common/DataTable.vue` 外壳有 `overflow-x:auto` 但未生效；内部 `.el-table__body-wrapper` 计算后 `overflow-x:hidden`；固定在右侧的操作列（`fixed="right"`）在半透明玻璃主题下出现内容穿透/鬼影；另见 F10（弹窗遮罩层级）。
- **现象**：关键列（结论、方法、检验员、操作）在默认宽度下看不到或浮在遮罩之上，数据密集区可读性受损，违反 AGENTS 5.1 红线①（数据密集区可读性优先）。
- **建议改法（GLM）**：
  1. 数据密集表格统一走 `.lims-panel`（高对比、弱模糊）；
  2. 让 DataTable 外壳的横向滚动真正生效（el-table 不设固定 `height` 时由外层容器控宽，或给 `.el-table__body-wrapper` 显式 `overflow-x:auto`）；
  3. 固定列背景实色化（不要透传底层内容），`fixed` 列阴影/边框按主题令牌重设；
  4. 抽屉内宽表给明确 `max-height` + 横向滚动，禁止右侧关键列默认裁切。
- **验收**：1366/1440/1920 三档宽度下列完整可见或可横向滚动；固定列无穿透。

### 🟠 F17 旧库迁移数据双重损坏：农药名被逗号切断 + 中文双重编码乱码（影响自动分派与判定可信度）

- **页面/链路**：项目标准库、项目分解自动套库、任务安排自动分派
- **证据文件**：`D:\lims\_logs\assign18.json`（`/assign/detail/18` 原样响应，16KB）
- **两类损坏（鲜食玉米产品库 62 项，源自 `lims.sql` 旧 `lib` 表经 V1 迁入）**：
  1. **逗号误切**：`db/migrations/V1__import_legacy_data.sql:98-100` 用
     `SUBSTRING_INDEX(testItem, ',', 1)` 按「名称,单位」切**第一个逗号**。但农药名本身含逗号，如「2,4-滴二甲胺盐,mg/kg」被切成 `item_name='2'`、`unit='4-滴二甲胺盐,mg/kg'`（items 1/2/3 均是：2,4-滴系列）。
  2. **UTF-8 双重编码**：`lims.sql`（806455 字节、无 BOM）导入 MySQL 时连接字符集不是 utf8mb4，导致中文以双重编码落库。纯 ASCII 正常，中文全乱：如 methods「参照NY/T 1434」→「åç§NY/T 1434」、「无指定」→「æ æå®」。V1 脚本虽有 `SET NAMES utf8mb4`，但**源表在导入 lims.sql 时已经损坏**。
- **业务影响（实测）**：
  - 鲜食玉米 62 项自动分派仅 23 项命中、**39 项待指派**，重要原因之一就是乱码方法名（「参照NY/T 1434」「无指定」）**永远匹配不上 `tester_method` 资质**；
  - 项目名在 UI/导出中显示为「2」，检验员无法识别；
  - 判定依据/单位被污染，报告与省平台导出的数据可信度受损。
- **建议改法（迁移内容设计 = GLM；重导执行 = 豆包）**：
  1. **重导 lims.sql**：导入命令显式 `mysql --default-character-set=utf8mb4`，并先确认目标库/连接 `character_set_client/connection/results=utf8mb4`；导入后先 `SELECT` 抽查中文再跑迁移；
  2. **修 V1 切分逻辑**：单位是最后一个逗号后的固定枚举（mg/kg、μg/kg、mg/100g、CFU/g、/ 等），改为「按最后一个逗号切单位」（`SUBSTRING_INDEX(testItem,',',-1)` 取单位、前面整体为名称），并对切出的单位做白名单校验，不命中白名单则整条进错误清单而不是静默切错；
  3. 迁移脚本补**数据质量断言 SELECT**（名称长度=1 且单位含逗号的行数应为 0；methods 含 `Ã/å/æ/ç` 等乱码特征字符的行数应为 0），不符合即失败（fail-loud）；
  4. 重导重迁后复核鲜食玉米 62 项的自动分派命中率与项目名/方法显示。
- **备注**：鲜食玉米产品库仅存在于 `lims.sql`，不在任何 `db/` 脚本中，无法靠重跑 seed 恢复，必须重导旧库。

### 🟠 F20 「待判定」单项可被人工放行进入 CMA 报告，报告正文该单项仍印「待判定」（合规风险）

- **页面/链路**：报告审核（S60→S70）→ 报告生成（S80→S90）
- **复现（DEMO-2026-004 鳜鱼，id=21）**：
  1. 该样品 3 项：孔雀石绿「不得检出」但缺检出限 → **待判定**；恩诺沙星 152>100 → 不合格；镉合格；
  2. 审核抽屉勾选「我已逐项确认上述异常项，仍要审核通过」→ 放行成功（红线流程本身正确）；
  3. 签发后生成 CMA 报告：**总述**正确写为「其中恩诺沙星超标，判定为不合格」，但**项目明细行第 1 项结论仍印「待判定」**；
  4. 报告生成列表上该样品整体结论徽章长期显示「待判定」，与「已签发/已出报告」并列。
- **问题本质**：CMA/CMA-CATL 报告是对外法律文书，**不允许出现未决结论项**。当前「勾选确认」只记录了 `abnormal_confirmed=1`，却**没有要求审核人对该单项作出明确裁决（合格/不合格及依据）**，放行后数据缺口被原样带进报告。
- **建议改法（GLM，S 级，涉及审核/报告引擎）**：
  1. 异常项清单中对每个 `PENDING` 项要求**逐条选择最终裁决结论（合格/不合格）+ 必填裁决说明**，落库到该单项的人工结论与来源（conclusionSource=人工判定）；未逐条裁决时「审核通过」保持禁用/400；
  2. 报告生成前增加校验：**任一单项结论为空/待判定 → 拒绝生成**（或必须已有人工裁决值），fail-loud；
  3. 报告明细行的单项结论只允许「合格/不合格」，不得出现「待判定」；
  4. 列表整体结论在有人工裁决后应聚合为确定值（合格/不合格），不要在 S80/S90 仍显示「待判定」。
- **保留**：审核红线（不勾选确认 400）、退回原因必填 400、总述自动归纳不合格——这些已实测正确，不要回退。

## 七、顺畅操作路径（七阶段最短路径，供交互优化对标）

> 目标：每个环节「**一屏知范围 → 一个主动作 → 一次确认 → 自动到下一环节**」。下表为当前应保证的最短路径；修复 F3 后即可全程无卡点。

| 阶段 | 页面 | 最短操作 | 系统应给的唯一关键反馈 |
|---|---|---|---|
| 0 登录 | /login | 工号+密码→登录 | 按角色出菜单；无权限给 403 指引（已具备） |
| 1 基础数据 | 方法资质/项目标准库 | 维护方法资质→维护产品库项目 | 资质/项目条数；无冗余状态 |

**交互优化原则**：
- 列表页主动作按钮区只保留「本环节当前状态可执行」的动作（F11/F29）；终态样品只给「查看/留痕」。

- 状态反馈一处不重复：同一指标只显示一次（F19）、同一状态只在一个位置表达（F16）、面包屑只留一条（F4）、提示语只出现一次（F7）。
